## Defects and data integrity

These are wrong-as-shown, not missing features.
Priority is highest here because incorrect numbers on screen undermine the whole premise of the demo.

### D1 - Fuel "laps remaining" is not reconciled with race distance

**Blocking.**
The fuel readout reports laps remaining that far exceeds the total laps in the race.
Fuel stops being a constraint, so every fuel-related strategy call the agent makes is meaningless.

Required: fuel figures and race distance must be consistent with each other and realistic against their labels.

See [Q1](#q1---is-in-race-refuelling-in-scope) before this gets implemented.

### D2 - Tyre age and current lap are out of sync

**Blocking.**
Tyre age showed 47 laps while the header showed lap 48.
The values lag each other by a lap.

Root cause is almost certainly that widgets read different keys independently (`telemetry:latest` vs `race:{id}:state` vs the `tyres` hash), each landing at a slightly different tick.

Required: all widgets must read from the same source, so a single rendered frame is internally consistent.
Recommended approach is to publish one atomic snapshot per tick carrying a monotonic sequence number plus lap, and have every widget render from that snapshot rather than fetching per-widget keys.
This also fixes any other cross-widget mismatch of the same class, not just tyre age.

### D3 - Brakes widget is clipped by the timing tower

**Blocking for demo polish.**
The brakes element is not fully visible on the website.
The timing element overlaps and cuts it off.

Required: brakes must be fully displayed without overlap at the demo resolution.

### D4 - Audit every channel for realism against its own label and units

**High.**
Broader than D1.
Confirm that each data type is realistic for the parameter it claims to be, including units, plausible ranges, and rate of change.

Reference for expected ranges is [`docs/f1-telemetry-data.md`](../../docs/f1-telemetry-data.md), and the models producing them are in [`docs/simulation-models.md`](../../docs/simulation-models.md).
I should report per-channel findings rather than silently adjusting constants, since several scaling factors are interdependent.

### F4 - Make Gemma attribution explicit on the alerts panel

**High, and directly tied to how the project is judged.**
It is not currently apparent that Gemma is interpreting the signals and generating the descriptions.

Wanted:
- Clear "generated by Gemma" attribution on agent output.
- A visible thinking / in-progress state while Gemma is generating.

The AI is present but unlabelled, so a viewer cannot tell which text is model-generated and which is a static rule firing.

### F5 - Model-first view for the alerts panel

Make it clear which model and which alert tier produced each item.
A model-first organisation of the alerts panel is preferred over the current chronological list.

| Tier | Produced by | Reaches driver |
|------|-------------|----------------|
| 2a | Deterministic rule engine | Instantly, no human |
| 2b | Statistical signal detection | Instantly, no human |
| 2c | TimesFM anomaly detection + Gemma interpretation | After engineer approval |

## Open questions

These change the implementation, so they are worth settling before the corresponding work starts.

### Q1 - Is in-race refuelling in scope?

The walkthrough noted that a regular race has multiple refuels.
Modern Formula 1 has banned in-race refuelling since 2010, and cars start with the entire race fuel load.
The existing docs already assume this: [`docs/simulation-models.md`](../../docs/simulation-models.md) tunes so that "100 kg lasts a full race (~57 laps)", and `races.starting_fuel_kg` is a single starting value with no refuel field anywhere in the schema.

This does not weaken D1, it sharpens the target:

- **If no refuelling** (matches real F1 and the current docs), the correct target is `fuel_laps_remaining` tracking slightly above `laps_remaining` for the whole race, with the margin being the actual strategy lever.
- **If we do want refuelling** in the simulation, that is a deliberate departure from real F1 and needs a schema change plus a pit-stop fuel decision for the agent.

Which one do we want?
I will not touch the fuel model until this is settled, because the two produce opposite behaviour.

### Q2 - How far does multi-vehicle go?

Does F3 mean:
- Several phones streaming as independent cars racing each other, or
- One real car plus synthetic rivals for gap and position context?

The second is far cheaper and gets the visual benefit.
The first requires per-vehicle sessions across ingestion, simulation state, alert routing, and the agent context.

### Q3 - Exact Gemma version string

The walkthrough referred to Gemma 4.
Before that label goes on screen I want to confirm the exact model and version being called, because an inaccurate model name in a Gemma-sponsored competition is a bad look.
Whatever string the UI shows should come from the actual configured model identifier rather than being hardcoded.
